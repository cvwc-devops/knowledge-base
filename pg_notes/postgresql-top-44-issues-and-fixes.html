ISSUE 01

Connection Exhaustion Connections

● Critical

The Problem

PostgreSQL allocates a fixed pool of connection slots set by max_connections. When all slots are taken, every new connection attempt fails immediately with a hard error — no queuing, no graceful degradation. This is a hard outage.

FATAL: sorry, too many clients already

The root cause is almost never "too many users." It is almost always: no connection pooler (each application thread holds a dedicated backend), a connection leak (the app opens connections and never closes them), or an idle-in-transaction pile-up.

Diagnostic Queries

-- Total usage and headroom
SELECT
  (SELECT setting::int FROM pg_settings WHERE name = 'max_connections') AS max_conn,
  count(*) AS used_conn,
  (SELECT setting::int FROM pg_settings WHERE name = 'max_connections') - count(*) AS available,
  round(100.0 * count(*) /
    (SELECT setting::int FROM pg_settings WHERE name = 'max_connections'), 1) AS pct_used
FROM pg_stat_activity;

-- Breakdown by application and state
SELECT
  application_name,
  state,
  count(*) AS cnt
FROM pg_stat_activity
WHERE pid != pg_backend_pid()
GROUP BY application_name, state
ORDER BY cnt DESC;

The Fix

Immediate — kill idle connections:

SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'idle'
  AND query_start < now() - interval '10 minutes'
  AND pid != pg_backend_pid();

Structural fix — PgBouncer in transaction mode:

# /etc/pgbouncer/pgbouncer.ini
[databases]
mydb = host=127.0.0.1 port=5432 dbname=mydb

[pgbouncer]
pool_mode = transaction
max_client_conn = 5000
default_pool_size = 25
min_pool_size = 5
reserve_pool_size = 5
server_idle_timeout = 600
# postgresql.conf — lower the server ceiling; pooler handles the rest
max_connections = 100
superuser_reserved_connections = 3
Connection exhaustion is a pooler problem, not a max_connections problem. Raising max_connections increases shared memory consumption and context-switching overhead without fixing the root cause. Deploy PgBouncer in transaction mode and keep your server-side connection count under 200.
ISSUE 02

Lock Contention & Blocking Chains Locks

● Critical

The Problem

PostgreSQL uses MVCC but still requires locks for writes. When two transactions try to modify the same row, or when a DDL statement needs an AccessExclusiveLock, one transaction must wait. If the blocker is itself waiting, you get a chain that can paralyse your entire application. The blocking chain is not visible in application logs — the application just hangs, CPU drops to zero, and DBA gets paged.

Diagnostic Queries

-- Full blocking chain with wait times (PostgreSQL 9.6+)
SELECT
  blocked.pid            AS waiting_pid,
  blocked.usename        AS waiting_user,
  blocked.query          AS waiting_query,
  blocking.pid           AS blocking_pid,
  blocking.usename       AS blocking_user,
  blocking.query         AS blocking_query,
  now() - blocked.query_start AS wait_duration
FROM pg_stat_activity AS blocked
JOIN pg_stat_activity AS blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0
ORDER BY wait_duration DESC;

The Fix

Terminate the root blocker:

SELECT pg_terminate_backend(12345); -- use blocking_pid from above

Keep transactions short — move work outside the transaction boundary:

-- BAD: holds lock while application "thinks"
BEGIN;
SELECT * FROM orders WHERE status = 'pending';
-- ... application does work for 30 seconds ...
UPDATE orders SET status = 'processing' WHERE id = 42;
COMMIT;

-- GOOD: fetch outside transaction; only lock during the write
SELECT * FROM orders WHERE status = 'pending';
BEGIN;
UPDATE orders SET status = 'processing' WHERE id = 42;
COMMIT;

Skip locked rows for queue patterns:

SELECT id, payload FROM job_queue
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;

Set lock_timeout to prevent indefinite waits:

lock_timeout = '5s'  -- postgresql.conf or SET per session
Use pg_blocking_pids() to find the root blocker immediately — terminate that PID, not a random symptom. Set lock_timeout on all application connections to guarantee no query waits forever. Keep transactions under one second in OLTP systems.
ISSUE 03

Deadlocks Locks

● Warning

The Problem

A deadlock happens when transaction A holds a lock that B needs, and B holds a lock that A needs. PostgreSQL detects this automatically and cancels one transaction. Deadlocks are not random — they follow predictable patterns in application code, almost always from updating multiple rows in inconsistent orders.

ERROR: deadlock detected DETAIL: Process 1234 waits for ShareLock on transaction 5678; blocked by process 5679. Process 5679 waits for ShareLock on transaction 5678; blocked by process 1234.

Diagnostic Queries

-- Count deadlocks per database since last stats reset
SELECT datname, deadlocks
FROM pg_stat_database
ORDER BY deadlocks DESC;
# Enable deadlock logging in postgresql.conf
log_lock_waits = on
deadlock_timeout = 1s

The Fix

Lock rows in a consistent, deterministic order:

-- Always update rows in the same order — prevents deadlocks
UPDATE accounts SET balance = balance - 100
WHERE id = ANY(ARRAY[1, 2])
ORDER BY id;  -- consistent ordering

Retry deadlocked transactions with exponential backoff:

import psycopg2, time, random
from psycopg2 import errors

def execute_with_retry(conn, fn, max_retries=3):
    for attempt in range(max_retries):
        try:
            with conn.cursor() as cur:
                fn(cur)
            conn.commit()
            return
        except errors.DeadlockDetected:
            conn.rollback()
            if attempt == max_retries - 1:
                raise
            time.sleep(0.1 * (2 ** attempt) + random.uniform(0, 0.1))
Deadlocks are always an application design issue. Lock rows in a consistent, deterministic order across all code paths. Enable log_lock_waits so deadlocks appear in your log aggregator. Build retry logic with exponential backoff for any transaction touching multiple rows that could conflict with concurrent transactions.
ISSUE 04

Idle-in-Transaction Connections Locks

● Warning

The Problem

An "idle in transaction" session has opened a BEGIN but is not executing any query. It holds all locks acquired so far and prevents VACUUM from cleaning rows it has read. A single stuck idle-in-transaction session can block VACUUM, hold row locks that block writes, and consume a connection slot indefinitely.

Diagnostic Queries

SELECT
  pid, usename, application_name, state,
  now() - state_change     AS idle_in_txn_duration,
  left(query, 100)         AS last_query
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'idle in transaction (aborted)')
ORDER BY idle_in_txn_duration DESC;

The Fix

-- Kill sessions idle in transaction for more than 5 minutes
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'idle in transaction (aborted)')
  AND state_change < now() - interval '5 minutes';
# postgresql.conf — automatically terminate idle-in-txn sessions
idle_in_transaction_session_timeout = '5min'
Set idle_in_transaction_session_timeout = '5min' in postgresql.conf. This is the single cheapest configuration change that prevents an entire class of production incidents. Never open a transaction and then wait for user input, a network call, or any slow operation inside it.
ISSUE 05

Transaction ID (XID) Wraparound Vacuum

● Critical

The Problem

PostgreSQL assigns a 32-bit transaction ID to every transaction. When the counter approaches 2 billion, PostgreSQL enters a failsafe mode and — if not addressed — shuts the entire cluster down to prevent data corruption. The preventive mechanism is VACUUM FREEZE. This is not theoretical — it has taken down production databases at major companies.

ERROR: database is not accepting commands to avoid wraparound data loss

Diagnostic Queries

-- Tables with the oldest XIDs (most at-risk)
SELECT
  n.nspname                            AS schema,
  c.relname                            AS table_name,
  age(c.relfrozenxid)                  AS xid_age,
  pg_size_pretty(pg_table_size(c.oid)) AS table_size,
  2000000000 - age(c.relfrozenxid)     AS txns_until_failsafe
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r'
  AND n.nspname NOT IN ('pg_catalog','information_schema')
ORDER BY xid_age DESC
LIMIT 20;

The Fix

Alert at 500 million. Treat 1 billion as a P0 incident.

-- Manual freeze for at-risk tables
VACUUM FREEZE VERBOSE my_large_table;
# postgresql.conf — more aggressive freeze schedule
autovacuum_freeze_max_age = 200000000
vacuum_freeze_table_age   = 150000000
-- Per-table override for rarely-updated tables
ALTER TABLE rarely_updated
  SET (autovacuum_freeze_max_age = 100000000);
XID wraparound is the PostgreSQL equivalent of a self-inflicted hard shutdown. Monitor age(relfrozenxid) on every table. Alert at 500 million. Never let autovacuum fall behind on long-lived, rarely-updated tables — they accumulate XID age silently and without warning.
ISSUE 06

Autovacuum Not Keeping Up Vacuum

● Warning

The Problem

Autovacuum reclaims dead tuples and updates planner statistics. When it cannot keep up with write load, tables bloat, plans degrade, and XID age creeps toward wraparound. The default autovacuum settings were designed for modest workloads — not tables receiving thousands of writes per minute.

Diagnostic Queries

SELECT
  schemaname, relname AS table_name,
  n_dead_tup, n_live_tup,
  round(n_dead_tup::numeric / nullif(n_live_tup, 0), 3) AS dead_ratio,
  last_autovacuum, last_autoanalyze,
  pg_size_pretty(pg_total_relation_size(schemaname||'.'||relname)) AS size
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC
LIMIT 20;

The Fix

-- Immediate: manual vacuum while tuning
VACUUM ANALYZE my_bloated_table;
# postgresql.conf — tune for write-heavy workloads
autovacuum_max_workers = 6
autovacuum_vacuum_scale_factor = 0.01     # was 0.2
autovacuum_analyze_scale_factor = 0.005   # was 0.1
autovacuum_vacuum_cost_delay = 2ms
autovacuum_vacuum_cost_limit = 400
-- Per-table override for hot tables
ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_analyze_scale_factor = 0.005,
  autovacuum_vacuum_cost_delay = 0,
  autovacuum_vacuum_cost_limit = 1000
);
Default autovacuum settings were designed for modest workloads. Any table receiving more than a few thousand writes per minute needs tuned per-table autovacuum parameters. Lower scale factors, increase worker count, reduce cost delay. Monitor n_dead_tup and last_autovacuum in your metrics pipeline — not just at incident time.
ISSUE 07

Table Bloat from Dead Tuples Vacuum

● Warning

The Problem

PostgreSQL's MVCC never overwrites rows in place. Every UPDATE writes a new row version; every DELETE marks the old row as dead. VACUUM reclaims space for reuse within the same file but does not return it to the OS by default. A bloated table wastes disk, slows sequential scans, and degrades cache hit ratio.

Diagnostic Queries

SELECT
  relname,
  pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size,
  n_dead_tup,
  n_live_tup,
  round(100.0 * n_dead_tup / nullif(n_live_tup, 0), 1) AS dead_pct
FROM pg_stat_user_tables
JOIN pg_class c USING (relname)
ORDER BY pg_total_relation_size(c.oid) DESC
LIMIT 20;

The Fix

pg_repack (online, preferred for production):

pg_repack -h localhost -U postgres -d mydb -t my_bloated_table

VACUUM FULL (requires maintenance window — blocks all access):

VACUUM FULL ANALYZE my_bloated_table;

Partition + DROP for time-series tables (best long-term solution):

CREATE TABLE events_2024_01 PARTITION OF events
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

-- Later: instant, no bloat, no VACUUM needed
DROP TABLE events_2023_01;
Use pg_repack for production tables — it runs online with minimal locking. For append-heavy tables, switch to range partitioning by time so old data can be dropped instantaneously. Never run VACUUM FULL on a production table without a maintenance window.
ISSUE 08

Index Bloat Indexes

● Performance

The Problem

B-tree indexes accumulate bloat just like tables. When rows are deleted or updated, index entries are marked dead but not immediately reclaimed. Index bloat causes larger index files consuming cache space, slower index scans, and increased write amplification on every write to the table.

Diagnostic Queries

SELECT
  schemaname, tablename, indexname,
  pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
  idx_scan, idx_tup_read
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC
LIMIT 20;

The Fix

-- REINDEX CONCURRENTLY — rebuilds without blocking reads/writes (PG 12+)
REINDEX INDEX CONCURRENTLY my_table_idx;
REINDEX TABLE CONCURRENTLY my_table;
-- Reduce future bloat with fillfactor
ALTER TABLE my_table SET (fillfactor = 70);
CREATE INDEX my_idx ON my_table(col) WITH (fillfactor = 70);
Schedule REINDEX CONCURRENTLY on your largest indexes quarterly, or more often on high-write tables. Set fillfactor below 100 on tables with frequent in-place updates to enable HOT (Heap-Only Tuple) updates that avoid index churn.
ISSUE 09

Missing Indexes Causing Sequential Scans Indexes

● Performance

The Problem

A sequential scan reads every page of a table regardless of how many rows match. On a 100-million-row table, a missing index turns a 1-millisecond lookup into a 10-second full scan. The planner chooses seq scans when no suitable index exists, statistics are stale, or a type mismatch prevents index use.

Diagnostic Queries

-- Tables with high sequential scan counts
SELECT
  schemaname, relname, seq_scan, idx_scan, n_live_tup,
  round(100.0 * seq_scan / nullif(seq_scan + idx_scan, 0), 1) AS pct_seq
FROM pg_stat_user_tables
WHERE n_live_tup > 10000 AND seq_scan > 100
ORDER BY seq_scan DESC
LIMIT 20;
-- Confirm the scan type for a specific query
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 12345;

The Fix

-- Single-column
CREATE INDEX CONCURRENTLY idx_orders_customer_id
  ON orders(customer_id);

-- Composite for filter + sort
CREATE INDEX CONCURRENTLY idx_orders_customer_status
  ON orders(customer_id, status, created_at DESC);

-- Partial index — smaller, faster, less write overhead
CREATE INDEX CONCURRENTLY idx_orders_pending
  ON orders(created_at)
  WHERE status = 'pending';
Monitor pg_stat_user_tables for tables where seq_scan is growing rapidly. Use EXPLAIN (ANALYZE, BUFFERS) to confirm every slow query's scan type. Create partial indexes for common filtered patterns. Never add an index without verifying with EXPLAIN that the planner actually uses it.
ISSUE 10

Unused Indexes Wasting Write Overhead Indexes

● Performance

The Problem

Every index is updated on every INSERT, UPDATE, and DELETE. An unused index is pure write overhead — CPU and I/O on every write with zero read benefit. Unused indexes on high-write tables can reduce write throughput by 5–15%.

Diagnostic Queries

-- Indexes never scanned since last stats reset
SELECT
  schemaname, relname AS table_name, indexrelname AS index_name,
  idx_scan AS times_used,
  pg_size_pretty(pg_relation_size(indexrelid))  AS index_size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND schemaname NOT IN ('pg_catalog','pg_toast')
ORDER BY pg_relation_size(indexrelid) DESC;

The Fix

-- Safe: DROP CONCURRENTLY does not block reads or writes
DROP INDEX CONCURRENTLY idx_orders_old_status;

Caveats: wait at least one week post-restart before trusting zero counts. Never drop unique indexes — they enforce constraints even if not used for reads.

Run the unused-index query monthly. Anything with idx_scan = 0 for more than two weeks is a candidate for removal. In microservices, each service should own only the indexes its own queries actually use.
ISSUE 11

Slow Queries Due to Bad Planner Estimates Query

● Warning

The Problem

The query planner uses statistics collected by ANALYZE to estimate row counts at each step. When estimates are wrong — stale stats, skewed distributions, or correlated columns — it chooses bad plans: wrong join type, wrong index, wrong scan method. A 10x discrepancy between estimated and actual rows in EXPLAIN ANALYZE is a red flag.

Diagnostic Queries

-- Compare actual vs estimated rows
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT o.*, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'pending'
  AND o.created_at > now() - interval '7 days';
-- Look for: "rows=5000 (actual rows=1234567)" = bad estimate

-- Inspect column statistics
SELECT attname, n_distinct, correlation,
  most_common_vals, most_common_freqs
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';

The Fix

-- Increase statistics target for skewed columns
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
ANALYZE orders;

-- Extended statistics for correlated columns (PG 10+)
CREATE STATISTICS orders_country_city ON country, city FROM orders;
ANALYZE orders;
Bad planner estimates are always a data or statistics problem. Increase statistics targets on skewed columns, use extended statistics for correlated column combinations, and always run ANALYZE after bulk loads. A 10x discrepancy between estimated and actual rows in EXPLAIN ANALYZE demands investigation.
ISSUE 12

Stale Statistics After Bulk Loads Query

● Warning

The Problem

After a large bulk load, table statistics may be dramatically wrong. Autovacuum's ANALYZE trigger fires when 20% of rows change — but loading 10 million rows into an empty table may not trigger it in time, and queries use plans based on empty or wrong statistics.

The Fix

-- Complete bulk-load workflow — always ANALYZE at the end
BEGIN;
ALTER TABLE staging_events DISABLE TRIGGER ALL;

COPY staging_events FROM '/data/events_2024.csv'
  WITH (FORMAT csv, HEADER true);

ALTER TABLE staging_events ENABLE TRIGGER ALL;
COMMIT;

-- Non-negotiable final step
VACUUM ANALYZE staging_events;
ANALYZE is fast. Running it explicitly after every bulk load costs almost nothing and prevents an entire class of plan-degradation incidents. Make VACUUM ANALYZE <table> the last step in every ETL script, migration, and data-load procedure.
ISSUE 13

work_mem Too Low Causing Disk Spills Memory

● Performance

The Problem

work_mem is the memory per sort or hash operation per query node. When it is exceeded, PostgreSQL spills to disk via temporary files. A single complex query can spawn dozens of sort or hash operations, each consuming up to work_mem bytes. The default of 4MB is often far too low.

Diagnostic Queries

-- In EXPLAIN ANALYZE output, look for:
-- "Sort Method: external merge  Disk: 42768kB"  ← spill (bad)
-- "Sort Method: quicksort  Memory: 4096kB"      ← in memory (good)

-- Queries spilling to disk (requires pg_stat_statements)
SELECT
  left(query, 120), calls,
  round(mean_exec_time::numeric, 2) AS avg_ms,
  temp_blks_written
FROM pg_stat_statements
WHERE temp_blks_written > 0
ORDER BY temp_blks_written DESC
LIMIT 10;

The Fix

# postgresql.conf — conservative global default
work_mem = 64MB

-- Per-role overrides for heavy users
ALTER ROLE analytics_user SET work_mem = '256MB';
ALTER ROLE app_user SET work_mem = '32MB';
Do not raise work_mem globally without calculating worst-case memory usage. Set a conservative global value (32–64MB) and use ALTER ROLE to give higher values to batch and analytics users. Monitor pg_stat_statements.temp_blks_written — any non-zero value means queries are spilling unnecessarily.
ISSUE 14

shared_buffers Undersized Memory

● Performance

The Problem

shared_buffers is PostgreSQL's internal page cache. The default 128MB is appropriate for a development laptop, not a production server with 64GB RAM. If it is too small, every query reads from the OS cache or disk — orders of magnitude slower than shared memory.

Diagnostic Queries

-- Overall cache hit ratio (should be > 99% on OLTP)
SELECT
  sum(heap_blks_hit) AS cache_hits,
  sum(heap_blks_read) AS disk_reads,
  round(
    100.0 * sum(heap_blks_hit)
    / nullif(sum(heap_blks_hit + heap_blks_read), 0), 2
  ) AS cache_hit_pct
FROM pg_statio_user_tables;

The Fix

# postgresql.conf
shared_buffers = 16GB         # 25% of 64GB total RAM
effective_cache_size = 48GB   # 75% of 64GB — planner hint, allocates nothing

# Enable huge pages on Linux for large shared_buffers
huge_pages = on
# /etc/sysctl.conf: vm.nr_hugepages = 8192
Set shared_buffers to 25% of total RAM. Set effective_cache_size to 75%. If the cache hit ratio is below 99% and you have free RAM, increase shared_buffers. Enable huge pages on Linux to reduce TLB pressure. A restart is required for changes to take effect.
ISSUE 15

Checkpoint Storms I/O

● Warning

The Problem

PostgreSQL periodically flushes dirty shared_buffer pages to data files in a checkpoint. If checkpoints happen too frequently — due to high write volume — they cause spikes of disk I/O, query latency spikes, and write amplification. The warning sign: checkpoints_req climbing in pg_stat_bgwriter.

Diagnostic Queries

SELECT
  checkpoints_timed,
  checkpoints_req,       -- forced by WAL segments filling — this is the problem
  checkpoint_write_time,
  checkpoint_sync_time,
  buffers_checkpoint,
  stats_reset
FROM pg_stat_bgwriter;

The Fix

# postgresql.conf
max_wal_size = 8GB                    # default: 1GB — give WAL more runway
min_wal_size = 1GB
checkpoint_completion_target = 0.9   # spread writes over 90% of interval
checkpoint_timeout = 15min            # default: 5min — longer between checkpoints
A healthy system has mostly checkpoints_timed, not checkpoints_req. If checkpoints_req is growing, increase max_wal_size, set checkpoint_completion_target = 0.9, and extend checkpoint_timeout. These three changes together dramatically smooth checkpoint I/O.
ISSUE 16

WAL Bloat Filling Disk WAL

● Critical

The Problem

WAL files accumulate on disk when inactive replication slots are not consumed (by far the most dangerous cause), wal_keep_size is set too high, or archiving is stalled. WAL filling the disk is an emergency — PostgreSQL cannot accept new writes.

Diagnostic Queries

-- WAL directory size
SELECT pg_size_pretty(sum(size)) AS wal_size FROM pg_ls_waldir();

-- Slots and their WAL retention (the most common culprit)
SELECT
  slot_name, active,
  pg_size_pretty(pg_current_wal_lsn() - confirmed_flush_lsn) AS wal_retained
FROM pg_replication_slots
ORDER BY (pg_current_wal_lsn() - confirmed_flush_lsn) DESC NULLS LAST;

The Fix

-- Drop inactive slots (most common emergency fix)
SELECT pg_drop_replication_slot(slot_name)
FROM pg_replication_slots
WHERE active = false;
# Cap WAL retention per slot — safety net (PostgreSQL 13+)
max_slot_wal_keep_size = 10GB
Inactive replication slots are the single most common cause of WAL filling disk. Set max_slot_wal_keep_size in PostgreSQL 13+ to cap retention. Alert when any slot's WAL retention exceeds 10GB. If disk fills due to WAL, drop inactive slots first — they are the likeliest culprit.
ISSUE 17

Replication Lag on Standbys Replication

● Critical

The Problem

When a standby cannot replay WAL as fast as the primary generates it, replication lag accumulates. A lagging standby serves stale reads and, on failover, represents data loss proportional to its lag. If lag grows indefinitely, the standby disconnects entirely.

Diagnostic Queries

-- On the primary: lag per connected standby
SELECT
  application_name, client_addr, state,
  (sent_lsn - replay_lsn)  AS bytes_lag,
  write_lag, flush_lag, replay_lag
FROM pg_stat_replication
ORDER BY bytes_lag DESC NULLS LAST;

-- On the standby: lag from its own view
SELECT
  now() - pg_last_xact_replay_timestamp() AS replication_lag,
  pg_last_wal_receive_lsn()               AS received_lsn,
  pg_last_wal_replay_lsn()               AS replayed_lsn;

The Fix

-- Diagnose where lag accumulates:
-- sent_lsn - write_lsn  = network bottleneck
-- write_lsn - flush_lsn = standby I/O bottleneck
-- flush_lsn - replay_lsn = standby CPU/replay bottleneck

# postgresql.conf (primary): compress WAL to reduce network transfer
wal_compression = on

# standby postgresql.conf (PostgreSQL 15+): parallel replay
recovery_parallelism = 4

# standby postgresql.conf: reduce conflict cancellations
hot_standby_feedback = on
Use the sent/write/flush/replay LSN chain to pinpoint where lag accumulates. Enable wal_compression to reduce network transfer. On PostgreSQL 15+, enable parallel WAL replay for high-write primaries. Alert when lag exceeds your RPO (recovery point objective).
ISSUE 18

Inactive Replication Slots Replication

● Critical

The Problem

An inactive replication slot silently retains all WAL generated since it was last consumed. Common causes: decommissioned standby whose slot was not dropped, deleted logical replication subscriber without DROP SUBSCRIPTION, or a crashed CDC connector. The slot grows at your write volume rate — it is a ticking clock.

Diagnostic Queries

SELECT
  slot_name, slot_type, active, active_pid,
  pg_size_pretty(pg_current_wal_lsn() - confirmed_flush_lsn) AS wal_retained,
  plugin
FROM pg_replication_slots
ORDER BY (pg_current_wal_lsn() - confirmed_flush_lsn) DESC NULLS LAST;

The Fix

-- Drop inactive slots
SELECT pg_drop_replication_slot('old_standby_slot');

-- Monitoring alert query — page if any inactive slot retains > 1GB
SELECT slot_name,
  pg_size_pretty(pg_current_wal_lsn() - confirmed_flush_lsn) AS retained
FROM pg_replication_slots
WHERE active = false
  AND (pg_current_wal_lsn() - confirmed_flush_lsn) > 1073741824;
Treat replication slot creation as a lifecycle event that requires cleanup. Any process that creates a slot must have a corresponding cleanup step when it exits. Set max_slot_wal_keep_size = 10GB as a safety net. Monitor slot WAL retention in your metrics pipeline.
ISSUE 19

ISSUE 21

Out-of-Memory (OOM) Kills Memory

● Critical

The Problem

The Linux OOM killer terminates processes when the system runs out of memory. An OOM kill of any PostgreSQL backend causes the entire cluster to restart, rolling back all in-flight transactions. Symptoms: dmesg shows Out of memory: Kill process (postgres), cluster restarts with no obvious cause in its own logs.

The Fix

# Calculate worst-case memory footprint first:
# shared_buffers
# + (max_connections × work_mem × avg_sort_ops_per_query)
# + (max_connections × 5MB per backend overhead)
# + (autovacuum_max_workers × maintenance_work_mem)
# Leave 30–40% of RAM for OS page cache

# Protect PostgreSQL from OOM killer (as root)
echo -1000 > /proc/$(pgrep -x postgres | head -1)/oom_score_adj
# systemd unit override: /etc/systemd/system/postgresql.service.d/oom.conf

ISSUE 24

N+1 Query Patterns from ORMs Query

● Performance

The Problem

N+1 is an ORM anti-pattern where loading N objects triggers N additional queries to load related data. A page that should run 2 queries runs 2002 instead. Each query is fast; the aggregate is catastrophic. PostgreSQL shows nothing unusual in pg_stat_activity — but pg_stat_statements reveals the pattern as enormous calls counts with low individual latency.

Diagnostic Queries

-- Find high-frequency parameterised queries (N+1 signature)
SELECT
  left(query, 120) AS query_pattern,
  calls,
  round(mean_exec_time::numeric, 3) AS avg_ms,
  round(total_exec_time::numeric / 1000, 1) AS total_sec
FROM pg_stat_statements
WHERE calls > 1000 AND mean_exec_time < 5
ORDER BY calls DESC
LIMIT 20;

The Fix

-- Fix: single JOIN instead of N separate queries
SELECT o.*, c.name, c.email
FROM orders o
JOIN customers c ON c.id = o.customer_id
LIMIT 1000;

# BAD:  Order.objects.all()[:1000]
# GOOD: Order.objects.select_related('customer').all()[:1000]
// Sequelize eager loading

  include: [{ model: Customer }],
  limit: 1000,
});

ISSUE 25

Partition Pruning Not Working Query

● Performance

The Problem

Declarative table partitioning (PostgreSQL 10+) uses partition pruning to skip irrelevant partitions. When pruning fails, a query scans every partition, negating all benefits of partitioning. Pruning fails when the filter uses a function on the partition key, there is a type mismatch, or enable_partition_pruning is off.

Diagnostic Queries

-- Does the plan prune partitions?
EXPLAIN (ANALYZE)
SELECT * FROM events
WHERE created_at BETWEEN '2024-01-01' AND '2024-01-31';
-- Look for: "Subplans Removed: N" — N partitions skipped
-- Missing = all partitions scanned (bad)

The Fix

-- BAD: function on partition key prevents pruning
SELECT * FROM events
WHERE date_trunc('month', created_at) = '2024-01-01';

-- GOOD: direct range comparison on the column
SELECT * FROM events
WHERE created_at >= '2024-01-01'
  AND created_at < '2024-02-01';
# postgresql.conf — enable partition-wise execution
enable_partition_pruning = on
enable_partitionwise_join = on
enable_partitionwise_aggregate = on
Partition pruning only works with direct comparisons on the partition key column, with compatible types, without wrapping functions. Always verify with EXPLAIN that Subplans Removed appears in the output. Use range predicates directly — never wrap the partition key in a function in the WHERE clause.
ISSUE 26

● Performance

The Problem

ISSUE 27

● Warning

The Problem

Major version upgrades improve the planner with new algorithms and cost model changes. While this almost always improves overall performance, specific queries can regress if the new planner makes different choices for a particular data distribution. A previously fast query becomes slow after an upgrade, with EXPLAIN showing a different plan type.

-- Step 2: increase statistics target for regressed columns

-- Step 3: use pg_hint_plan for a targeted fix

ISSUE 28

Index Not Used Due to Type Mismatch Indexes

● Performance

The Problem

PostgreSQL is strict about types. If a query filters a column with a different type than the column's declared type, the planner cannot use the index without an implicit cast on the column side — which makes the index unusable. This causes a silent sequential scan on a table with a perfectly good index. Classic examples: column is integer, query passes a varchar like WHERE id = '123'.

Diagnostic Queries

-- EXPLAIN reveals implicit casts
EXPLAIN SELECT * FROM orders WHERE id = '123';
-- "Filter: (id::text = '123')"   → cast on COLUMN side = index cannot be used!
-- "Filter: (id = '123'::integer)" → cast on VALUE side = index can still be used

The Fix

# Python — pass the correct type
# BAD:  cursor.execute("... WHERE id = %s", ("123",))  # string
# GOOD: cursor.execute("... WHERE id = %s", (123,))    # integer
-- Use explicit casts in the query
SELECT * FROM orders WHERE id = '123'::integer;

-- If you cannot change the query: functional index on the cast
CREATE INDEX idx_orders_id_text ON orders(id::text);
-- Now: WHERE id::text = '123' can use this index
Type mismatches silently cause sequential scans on indexed columns. When you see a cast on the column side in EXPLAIN output (e.g., id::text), the index cannot be used. Fix the root cause in the application layer; use functional indexes only as a last resort.
ISSUE 29

Slow COUNT(*) on Large Tables Query

● Performance

The Problem

SELECT COUNT(*) FROM large_table requires a sequential scan in PostgreSQL because MVCC means different transactions see different row counts — there is no single global total. On 100 million rows, this can take 10+ seconds.

The Fix

-- Option 1: approximate count — instant, within ~1%
SELECT reltuples::bigint AS approx_count
FROM pg_class WHERE relname = 'events';

-- Option 2: filtered count via index only scan (fast)
SELECT COUNT(*) FROM orders WHERE status = 'pending';
-- Uses index on (status) — not a full seq scan

-- Option 3: counter table maintained by triggers
CREATE TABLE table_counts (table_name text PRIMARY KEY, cnt bigint DEFAULT 0);

CREATE OR REPLACE FUNCTION update_order_count() RETURNS trigger AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    UPDATE table_counts SET cnt = cnt + 1 WHERE table_name = 'orders';
  ELSIF TG_OP = 'DELETE' THEN
    UPDATE table_counts SET cnt = cnt - 1 WHERE table_name = 'orders';
  END IF;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;
Exact COUNT(*) on large tables is expensive by design in MVCC databases. For dashboards, reltuples approximations are accurate enough (within 1%) and return instantly. Reserve exact counts for business-critical operations. If you need exact real-time counts, maintain a counter table with triggers.
ISSUE 30

LIKE Queries Ignoring Indexes Indexes

● Performance

The Problem

B-tree indexes support LIKE 'prefix%' (prefix match) but not LIKE '%suffix' or LIKE '%infix%'. The standard operator class is needed for prefix LIKE in non-C locales, and a pg_trgm trigram index is needed for arbitrary substring searches.

The Fix

-- Prefix LIKE: use text_pattern_ops operator class
CREATE INDEX idx_products_name_pattern
  ON products(name text_pattern_ops);

SELECT * FROM products WHERE name LIKE 'apple%';  -- uses index
-- Substring LIKE: use pg_trgm GIN index
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_products_name_trgm
  ON products USING gin(name gin_trgm_ops);

SELECT * FROM products WHERE name LIKE '%apple%';    -- uses index
SELECT * FROM products WHERE name ILIKE '%Apple%';   -- case-insensitive!
-- Case-insensitive exact match: functional index on lower()
CREATE INDEX idx_products_name_lower ON products(lower(name));
SELECT * FROM products WHERE lower(name) = lower('Apple');
B-tree indexes do not help with LIKE '%substring%'. Install pg_trgm and create a GIN index for any column where substring searches are common. For prefix-only LIKE 'prefix%', use the text_pattern_ops operator class. For case-insensitive matches, use a functional index on lower(column) or the citext type.
ISSUE 31

JSON/JSONB Query Performance Query

● Performance

The Problem

JSONB is powerful but querying deeply nested JSON without proper indexing causes sequential scans and slow extraction. Common traps: querying on a JSON key without an index, missing GIN indexes, and storing data in JSONB that should be in normalised columns.

The Fix

-- Full GIN index: supports @>, ?, ?|, ?& operators
CREATE INDEX idx_events_data_gin ON events USING gin(data);

SELECT * FROM events WHERE data @> '{"event_type": "click"}';  -- index used

-- Functional index for specific key access (smaller, faster)
CREATE INDEX idx_events_event_type ON events((data->>'event_type'));
SELECT * FROM events WHERE data->>'event_type' = 'click';  -- index used

CREATE INDEX idx_events_user_id ON events(user_id);
Use jsonb_path_ops GIN index for @> and @? queries — smaller and faster than the default GIN. Use functional indexes on specific frequently-queried keys. If you always filter on the same JSONB fields, extract them to generated columns and index those instead. Never use JSONB as a substitute for schema design.
ISSUE 32

Full-Text Search Performance Query

● Performance

The Problem

PostgreSQL's built-in full-text search is fast when properly indexed, brutally slow when not. The most common mistake: computing to_tsvector() inline in every WHERE clause instead of storing it in a pre-computed column. This forces a full sequential scan and recomputes the vector for every row.

The Fix

-- Step 1: store tsvector as a generated column
ALTER TABLE articles
  ADD COLUMN search_vector tsvector
  GENERATED ALWAYS AS (
    to_tsvector('english',
      coalesce(title, '') || ' ' || coalesce(body, ''))
  ) STORED;

-- Step 2: GIN index on the stored vector
CREATE INDEX idx_articles_search ON articles USING gin(search_vector);

-- Step 3: query using the column (fast!)
SELECT id, title,
  ts_rank(search_vector, query) AS relevance_rank
FROM articles,
  plainto_tsquery('english', 'postgres performance') query
WHERE search_vector @@ query
ORDER BY relevance_rank DESC
LIMIT 20;
Store tsvector as a GENERATED ALWAYS AS ... STORED column and index it with GIN. Never compute to_tsvector() inline in a WHERE clause on a large table. Use plainto_tsquery for user input, and websearch_to_tsquery (PostgreSQL 11+) for Google-style query syntax.
ISSUE 33

Sequence Exhaustion Schema

● Critical

The Problem

SERIAL uses a 32-bit integer (max ~2.1 billion). In high-volume systems, this is reachable. When it is reached, inserts fail permanently until the column type is changed — a complex operation under pressure.

ERROR: nextval: reached maximum value of sequence "users_id_seq" (2147483647)

Diagnostic Queries

-- All sequences: current value, max, percentage used
SELECT
  s.relname AS sequence_name,
  format_type(t.seqtypid, null) AS data_type,
  t.seqmax AS max_value,
  last_value,
  round(100.0 * last_value / t.seqmax, 2) AS pct_used
FROM pg_class s
JOIN pg_sequence t ON t.seqrelid = s.oid
WHERE s.relkind = 'S'
ORDER BY pct_used DESC NULLS LAST;

The Fix

-- Convert SERIAL (integer) to BIGSERIAL (bigint)
ALTER SEQUENCE users_id_seq AS bigint;
ALTER TABLE users ALTER COLUMN id TYPE bigint;

-- New tables: always use BIGSERIAL or identity columns
CREATE TABLE users (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL
);

-- Or UUID — eliminates sequence exhaustion entirely
CREATE TABLE events (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),  -- PG 13+
  created_at timestamptz DEFAULT now()
);
Always use BIGSERIAL or bigint GENERATED AS IDENTITY for any table that could grow large. Run the sequence exhaustion query monthly on production. Alert when any integer sequence exceeds 75% usage. Migration to bigint must happen before exhaustion — it is complex under pressure.
ISSUE 34

Constraint Violations at Scale Schema

● Warning

The Problem

At scale, unique constraint violations from concurrent inserts (race conditions), foreign key violations during bulk loads, and check constraint failures all surface in ways that were invisible at small scale. They cause transaction rollbacks and application errors.

The Fix

-- Atomic upsert — no race conditions
INSERT INTO users (email, name) VALUES ('a@b.com', 'Alice')
ON CONFLICT (email) DO UPDATE
  SET name = EXCLUDED.name, updated_at = now();

-- Bulk load with FK deferral
BEGIN;
SET CONSTRAINTS ALL DEFERRED;
COPY orders FROM '/data/orders.csv' WITH (FORMAT csv);
COPY order_items FROM '/data/items.csv' WITH (FORMAT csv);
COMMIT;  -- FK checks run here, not mid-transaction
Use INSERT ... ON CONFLICT instead of application-level "check then insert" — it is atomic and race-condition-free. Defer FK constraints for bulk loads. Make FK constraints deferrable for complex multi-table inserts that need to succeed within a single transaction.
ISSUE 35

Foreign Key Locking Overhead Schema

● Warning

The Problem

FK constraints cause implicit lock acquisitions on every write. Without an index on the FK column in the child table, every DELETE from the parent table does a full sequential scan of the child table. PostgreSQL does not create these indexes automatically — it is one of the most commonly missed optimisations in schema design.

The Fix

-- Always index FK columns on the child table
CREATE INDEX CONCURRENTLY idx_order_items_order_id
  ON order_items(order_id);

CREATE INDEX CONCURRENTLY idx_order_items_product_id
  ON order_items(product_id);
-- Batch deletes to reduce lock contention
DO $$
DECLARE deleted int;
BEGIN
  LOOP
    DELETE FROM orders
    WHERE id IN (
      SELECT id FROM orders
      WHERE status = 'archived' AND created_at < now() - interval '2 years'
      LIMIT 1000
    );
    GET DIAGNOSTICS deleted = ROW_COUNT;
    EXIT WHEN deleted = 0;
    PERFORM pg_sleep(0.1);
  END LOOP;
END $$;
Always index FK columns on the referencing (child) table — PostgreSQL does not do this automatically. An unindexed FK column causes a full sequential scan of the child table on every DELETE from the parent. Run a check for missing FK indexes as part of every schema review.
ISSUE 36

Long-Running Schema Migrations Operations

● Warning

The Problem

Schema changes acquire locks that block application queries for their entire duration. A 10-minute migration holds a lock for 10 minutes — every query against that table queues up, eventually exhausting connections.

The Fix

-- BAD: blocks reads AND writes for the duration on large tables
CREATE INDEX idx_orders_status ON orders(status);

-- GOOD: does not block reads or writes
CREATE INDEX CONCURRENTLY idx_orders_status ON orders(status);
-- Fail fast rather than queue — set in migration scripts
SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN priority integer;
-- Fails cleanly if it cannot get the lock; retry during low-traffic window
-- Two-step constraint for zero-downtime addition
ALTER TABLE orders
  ADD CONSTRAINT chk_amount_positive CHECK (amount > 0) NOT VALID;

ALTER TABLE orders VALIDATE CONSTRAINT chk_amount_positive;
-- ShareUpdateExclusiveLock — reads and writes continue
Always use CREATE INDEX CONCURRENTLY for production indexes. Set lock_timeout = '2s' in migration scripts to fail fast rather than queue. Use the expand-contract pattern for column renames. Test migrations on a production-sized data copy — 30 seconds on staging may be 30 minutes on production.
ISSUE 37

Table-Level Lock from ALTER TABLE Operations

● Warning

The Problem

Many ALTER TABLE commands acquire AccessExclusiveLock, blocking all reads and writes. Some also rewrite the entire table, making them O(n) operations that can take hours on large tables.

The Fix

ADD COLUMN (nullable, no default)NoYes (instant)
ADD COLUMN with default (PG 11+)NoYes (instant)

ISSUE 38

Connection Storms After Restart Connections

● Warning

The Problem

When PostgreSQL restarts, all application connection pools try to reconnect simultaneously. This storm overwhelms PostgreSQL's connection setup overhead and causes cascading timeouts. PgBouncer, when deployed, can buffer the storm entirely.

The Fix

import psycopg2, time, random

def connect_with_backoff(dsn, max_retries=10):
    for attempt in range(max_retries):
        try:
            return psycopg2.connect(dsn)
        except psycopg2.OperationalError:
            if attempt == max_retries - 1:
                raise
            sleep = min((2 ** attempt) + random.uniform(0, 1), 60)
            time.sleep(sleep)
# pgbouncer.ini — buffer reconnect storms
query_wait_timeout = 30      # clients wait up to 30s for a server
server_connect_timeout = 15
server_login_retry = 15
Implement exponential backoff with jitter in your connection retry logic — never retry immediately. PgBouncer absorbs reconnect storms by queuing clients while PostgreSQL recovers. Set query_wait_timeout so queued clients fail gracefully if recovery takes too long.
ISSUE 39

Logical Replication Lag and Conflicts Replication

● Warning

The Problem

Logical replication (PostgreSQL 10+) has unique failure modes: unique constraint conflicts when the subscriber has a row the publisher tries to INSERT, replication lag, worker crashes, and schema drift between publisher and subscriber. Conflicts require manual intervention — PostgreSQL cannot auto-resolve them.

Diagnostic Queries

-- On publisher: slot lag

-- Resolve a unique key conflict on the subscriber

ISSUE 40

ISSUE 41

Point-in-Time Recovery Misconfiguration Backups

● Critical

The Problem

PITR allows restoring to any moment in time by replaying WAL from a base backup. Misconfiguration causes PITR to fail when you need it most: archive_mode = off, silent archive_command failures, or WAL archives that accumulate but are never tested.

Diagnostic Queries

-- Check archiving health daily in monitoring
SELECT
  archived_count, last_archived_wal, last_archived_time,
  failed_count, last_failed_wal, last_failed_time
FROM pg_stat_archiver;

The Fix

# postgresql.conf — enable WAL archiving
wal_level = replica
archive_mode = on
archive_command = 'wal-g wal-push %p'  # WAL-G to S3
# Test PITR recovery monthly
wal-g backup-fetch /var/lib/postgresql/14/restore LATEST

# recovery.signal triggers recovery mode (PostgreSQL 12+)
touch /var/lib/postgresql/14/restore/recovery.signal

# postgresql.conf on restore instance
restore_command = 'wal-g wal-fetch %f %p'
recovery_target_time = '2024-01-15 14:30:00'
recovery_target_action = 'promote'
PITR is only as good as your most recent tested restore. Verify pg_stat_archiver.failed_count = 0 daily in monitoring. Run a full PITR restore test monthly. Know your RTO: calculate base backup restore time plus WAL replay time and verify it against your recovery time objective.
ISSUE 42

SSL/TLS Connection Issues Security

● Warning

The Problem

Common SSL/TLS failures: expired certificates causing connection failures, hostname mismatches causing verification failures, applications using sslmode=disable when the server requires SSL, and certificate renewal not being automated.

The Fix

# postgresql.conf
ssl = on
ssl_cert_file = 'server.crt'
ssl_key_file = 'server.key'
ssl_min_protocol_version = 'TLSv1.2'

# pg_hba.conf — require SSL for remote connections
local   all  all                    peer
hostssl all  all  0.0.0.0/0        scram-sha-256
# Application — use verify-full (not just require)
conn = psycopg2.connect(
    host="mydb.example.com",
    sslmode="verify-full",      # checks both encryption AND hostname
    sslrootcert="/etc/ssl/certs/root.crt"
)
# Check certificate expiry — add to monitoring
openssl x509 -in /var/lib/postgresql/14/main/server.crt -noout -dates
Use sslmode=verify-full in application connection strings — not require or disable. verify-full checks both encryption and hostname, preventing man-in-the-middle attacks. Automate certificate renewal with Let's Encrypt + certbot. Monitor certificate expiry dates in your alerting system.
ISSUE 43

Extension Conflicts and Version Mismatches Operations

● Warning

The Problem

Extensions can conflict with each other, with the PostgreSQL version, or with themselves across schema changes. The most common failure after a major version upgrade: extensions installed at an old version that need updating before they work correctly with the new PostgreSQL.

Diagnostic Queries

-- All installed extensions with versions and available updates
SELECT
  name, installed_version, default_version,
  installed_version != default_version AS needs_update
FROM pg_available_extensions
WHERE installed_version IS NOT NULL
ORDER BY needs_update DESC;

The Fix

-- After a major PostgreSQL upgrade: update all extensions
ALTER EXTENSION postgis UPDATE;
ALTER EXTENSION pg_stat_statements UPDATE;
ALTER EXTENSION pg_trgm UPDATE;

-- Fix a broken install
DROP EXTENSION IF NOT EXISTS pg_trgm CASCADE;
CREATE EXTENSION pg_trgm;

# Validate shared_preload_libraries before restarting
ls /usr/lib/postgresql/14/lib/pg_stat_statements.so
postgres --config-file=/etc/postgresql/14/main/postgresql.conf \
  -C shared_preload_libraries
After every major PostgreSQL version upgrade, run ALTER EXTENSION <name> UPDATE for all installed extensions. Before adding to shared_preload_libraries, verify the extension's .so file exists on disk. Keep a registry of all installed extensions and their required PostgreSQL version ranges.
ISSUE 44

Corrupt Indexes and Data Pages Integrity

● Critical

The Problem

Data corruption is rare but real. Caused by storage hardware failure, ECC RAM failures, kernel or filesystem bugs. Symptoms include ERROR: invalid page in block N, queries returning unexpected NULL values, or pg_dump failing on specific tables.

ERROR: invalid page in block 42 of relation base/16384/24601 ERROR: could not read block 42 in file "base/16384/24601": read only 0 of 8192 bytes

Diagnostic Queries

-- Check for index corruption (requires amcheck)
CREATE EXTENSION IF NOT EXISTS amcheck;
SELECT bt_index_check('my_table_pkey');          -- quick check
SELECT bt_index_parent_check('my_table_pkey', true); -- thorough + heap
# Check data checksums (PostgreSQL 12+)
pg_checksums -D /var/lib/postgresql/14/main --check

The Fix

-- Step 1: rebuild the index — safest first fix
REINDEX INDEX CONCURRENTLY my_corrupt_index;
REINDEX TABLE CONCURRENTLY my_table;

-- Step 2: if the heap page is corrupt (data loss risk — use only if no backup)
SET zero_damaged_pages = on;  -- fills corrupt pages with zeros instead of erroring
SELECT * FROM my_table;
RESET zero_damaged_pages;
CREATE TABLE my_table_recovered AS SELECT * FROM my_table;
DROP TABLE my_table;
ALTER TABLE my_table_recovered RENAME TO my_table;
# Enable checksums on an existing cluster (PostgreSQL 12+)
pg_ctl stop -D /var/lib/postgresql/14/main
pg_checksums --enable -D /var/lib/postgresql/14/main
pg_ctl start -D /var/lib/postgresql/14/main
# Non-negotiable durability settings — NEVER change these in production
fsync = on
synchronous_commit = on
Enable data checksums with pg_checksums --enable on all production PostgreSQL 12+ clusters. Run bt_index_check() from amcheck periodically on critical indexes. fsync = on is non-negotiable — setting it to off trades your data's durability for speed and will corrupt your entire cluster on any crash.

Closing: Five Root Causes Behind Every Incident

Every issue in this guide traces back to one of five root causes:

  1. Resource limits not tuned to workload — max_connections, work_mem, shared_buffers, autovacuum workers
  2. Missing operational discipline — no ANALYZE after bulk loads, no backup testing, no monitoring
  3. Schema design gaps — missing FK indexes, wrong data types, unpartitioned time-series tables
  4. Reactive instead of proactive monitoring — discovering replication lag, XID age, and connection exhaustion only during incidents
  5. Lock management failures — long transactions, missing lock_timeout, no idle_in_transaction_session_timeout

All five are fixable with configuration, schema review, and metrics. PostgreSQL surfaces everything you need to know through pg_stat_* views — you just have to listen before things go wrong.

Quick Reference: Essential Monitoring Queries

-- 1. Connection health
SELECT state, count(*) FROM pg_stat_activity GROUP BY state ORDER BY count DESC;

-- 2. Blocking chains
SELECT blocked.pid, blocking.pid AS blocking_pid,
  now() - blocked.query_start AS wait, blocked.query AS waiting_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;

-- 3. XID wraparound risk (top 5)
SELECT relname, age(relfrozenxid) AS xid_age
FROM pg_class WHERE relkind = 'r'
ORDER BY xid_age DESC LIMIT 5;

-- 4. Autovacuum lag
SELECT relname, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 100000 ORDER BY n_dead_tup DESC LIMIT 10;

-- 5. Replication slot WAL retention
SELECT slot_name, active,
  pg_size_pretty(pg_current_wal_lsn() - confirmed_flush_lsn) AS wal_retained
FROM pg_replication_slots ORDER BY 3 DESC;

-- 6. Database cache hit ratio
SELECT round(
  100.0 * sum(blks_hit) / nullif(sum(blks_hit + blks_read), 0), 2
) AS cache_hit_pct
FROM pg_stat_database
WHERE datname NOT IN ('template0','template1');

-- 7. Sequence exhaustion (integer sequences)
SELECT s.relname AS seq, round(100.0 * last_value / seqmax, 2) AS pct_used
FROM pg_class s JOIN pg_sequence t ON t.seqrelid = s.oid
WHERE s.relkind = 'S' AND t.seqtypid = 'integer'::regtype::oid
ORDER BY pct_used DESC;

-- 8. Idle-in-transaction sessions
SELECT pid, usename, now() - state_change AS idle_duration, left(query, 80)
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'idle in transaction (aborted)')
ORDER BY idle_duration DESC;
